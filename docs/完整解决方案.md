# git-ai Windows 虚拟机挂起问题：综合分析报告与完整解决方案

**项目**: git-ai
**分析日期**: 2026-04-20
**分析环境**: Windows 10 中文版虚拟机，磁盘 I/O 上限 ~300KB/s
**综合报告**: 基于三份独立源码分析整合，覆盖 `分析报告.md`、`评估报告.md`、`Claude分析报告_git-ai虚拟机挂起问题.md`

---

## 一、问题描述

用户在高延迟、低性能虚拟机环境中使用 `git-ai` 进行 AI 编码占比统计时，遇到以下问题：

- `git-ai` 后台进程经常挂起/僵死
- 部分 AI 改动没有被计入最终统计
- `ai-code` 读取到的 AI 编码占比偏低
- 问题不是随机出现，而是与后台是否稳定强相关

## 二、三份报告核心观点对比

| 维度 | 分析报告.md | 评估报告.md | Claude分析报告（Tokio根因） |
|------|-------------|-------------|---------------------------|
| **分析视角** | 采集链路可靠性 | 架构层最终一致性 + 写放大 | Tokio 异步运行时阻塞线程池耗尽 |
| **最核心问题** | `exit(0)` 吞掉错误，上层无法重试 | checkpoint 依赖 + note 可见性延迟 | JSONL 全量读写 + blocking 线程池耗尽 |
| **超时问题** | bash hook 1500ms/4000ms 超时后 fallback；pre-snapshot 丢失不回退 | wrapper state 750ms；post-commit 500ms | daemon control 10s；blocking 线程池默认 ~10 个 |
| **错误传播** | 多个失败路径 `exit(0)`，上层不知失败 | 最终一致性，ai-code 不等稳定就读 | Tokio 阻塞传播，daemon 僵死 |
| **新增发现** | pre-snapshot 消费后立刻删，不留 retry 机会；`unwrap_or_default()` 会静默抹掉损坏的 checkpoint | Windows 安装流程主动关闭 async；无通用 AI 上下文恢复 | telemetry flush 在 `spawn_blocking` 中同步 HTTP + SQLite；300KB/s 下量化影响 |
| **数据丢失根因** | 静默失败 + 快照无 retry 机会 | checkpoint 丢 → 统计丢（无通用补偿） | blocking 线程池耗尽 → daemon 无响应 → 任务链中断 |

### 三份报告的共识（无争议事实）

1. **working log 不是追加写入，而是每次全量重写** — `src/git/repo_storage.rs`，三份报告均独立定位此问题
2. **bash hook 超时后直接 fallback** — `src/commands/checkpoint_agent/bash_tool.rs`，不报硬错误
3. **post-commit note 只等 500ms** — `src/commands/git_handlers.rs`，note 未生成就返回
4. **daemon wrapper state 等待仅 750ms** — `src/daemon.rs`，慢盘下极易超时
5. **Windows 官方安装流程主动关闭 async** — `.github/workflows/install-scripts-local.yml:183`，说明项目自身已认知风险
6. **`GIT_AI_SLOW_VM` 仅覆盖锁超时** — 其他所有超时点均未响应此环境变量

### 各自独有的发现（互相补充）

**分析报告.md 独有**：
- `exit(0)` 吞错是"漏记长期存在"的决定性原因
- `load_and_consume_snapshot()` 先读后删，无 retry 机会
- `unwrap_or_default()` 会静默覆盖损坏的 checkpoint 文件
- bash pre-snapshot 丢失后有 `git_status_fallback()` 实现但未调用

**评估报告.md 独有**：
- trace ingest 积压可达 1 分钟以上（源码注释 `src/daemon.rs:4899`）
- daemon checkpoint 前还要等 trace ingest 追平，不是有序处理
- commit replay 只对 bash in-flight 有补偿，无通用 Claude AI 上下文恢复
- `ai-code` 必须在统计链路稳定后读取，不能"调用完立即读"

**Claude分析报告独有**：
- Tokio blocking 线程池耗尽是 daemon 僵死的精确机制
- 300KB/s 下的量化影响：5MB 文件读写各需 17s+
- telemetry flush 在 `spawn_blocking` 中同步 HTTP + SQLite 阻塞整个 flush 循环
- Windows `LockFile` 每次 `libloading::Library::new("kernel32.dll")` 未缓存句柄

## 三、根本原因归纳

将三份报告综合后，问题根因分为四个层次：

### 根因 1：错误传播链断裂（最关键）

多个关键失败点以 `exit(0)` 退出，返回码为 0（成功）。这导致：

- 上层 `ai-code` / daemon 不知道 checkpoint 实际失败
- 没有重试机制
- 静默丢失数据

**涉及代码**（三份报告交叉验证）：
- `src/commands/git_ai_handlers.rs:441, 458, 1251, 1341` — preset 解析失败 / checkpoint 执行失败 / 本地 checkpoint 失败 均 `exit(0)`
- `src/commands/checkpoint_agent/bash_tool.rs:1671` — pre-snapshot 找不到直接 fallback，不报错误
- `src/git/repo_storage.rs:392` — `read_all_checkpoints().unwrap_or_default()` 读失败当空文件

### 根因 2：I/O 写放大在慢盘上被严重放大

| 操作 | 文件数/大小 | 300KB/s 单次耗时 | 频率 |
|------|------------|-----------------|------|
| 每文件 blob 写入 | N 个文件 | ~0.3s/文件 | 每次 checkpoint |
| captured checkpoint 二次 blob | N 个文件 | ~0.3s/文件 | 每次 explicit capture |
| manifest 写入 | 1 个文件 | ~0.1s | 每次 captured checkpoint |
| checkpoints.jsonl 全量重写 | 整个文件 | 3~17s+（取决于文件大小） | **每次 checkpoint** |
| SQLite WAL 写入 | metrics + internal DB | 碎片化，总计 1~5s | 持续后台 |

**单次 `git commit` 归因流程**中，`checkpoints.jsonl` 被读写 2-3 次：
- post-commit hook `mutate_all_checkpoints`：读 + 写
- daemon trace 处理：读
- daemon checkpoint side effect：读 + 写

在 300KB/s 下，一个稍大的工作日志文件（5MB）的单次读写就需要 **17 秒**，整个归因链路的阻塞时间可达 **30-50 秒**。

### 根因 3：异步路径在 Windows 慢机下设计预算不匹配

| 超时点 | 当前值 | 300KB/s 实际需求 | 后果 |
|--------|--------|-----------------|------|
| bash hook walk timeout | 1500ms | 可能需要 10s+ | 直接 fallback |
| bash hook hook timeout | 4000ms | 可能需要 20s+ | 直接 fallback |
| wrapper state 等待 | 750ms | 可能需要 5s+ | 状态覆盖失败 |
| post-commit note 等待 | 500ms | 可能需要 10s+ | 读到旧统计 |
| daemon startup | 5000ms | 可能需要 15s+ | 误判 daemon 未启动 |
| daemon control response | 10s | blocking 线程池耗尽时无上限 | 控制连接超时 |
| git proxy timeout | 20s + 1 retry | 尚可接受 | — |
| checkpoint lock timeout | 240s（SLOW_VM 下 480s） | 可能仍不够 | 锁超时报错 |

关键问题：**没有一揽子慢机模式**，`GIT_AI_SLOW_VM=1` 只覆盖了锁超时一个点。

### 根因 4：采集链路过长 + 无通用补偿

```
checkpoint → working log → post-commit → refs/notes/ai → stats
    ↑ 失败直接丢     ↑ 失败静默丢      ↑ 500ms 不等
```

链路中任意一步失败，本次 AI 改动就无法进入统计。补偿机制（commit replay）**仅覆盖 bash in-flight 场景**，普通 Claude 文件编辑失败后无通用补救。

## 四、故障机制量化模型

### Tokio Blocking 线程池耗尽（新增解释）

```
Tokio 多线程运行时
  ├─ worker threads (~CPU 核数)：处理 async 任务
  └─ blocking threads（默认 ~512 个并发槽位，实际 ~10 个线程）

blocking 线程用途：
  ├─ checkpoint::run() 中的 git diff / 文件读取 / SQLite / JSONL 读写
  ├─ telemetry flush (spawn_blocking)
  ├─ file state saving (smol 但部分仍同步)
  └─ daemon IPC block_on

在 300KB/s 下：
  ├─ 1 个 checkpoint 阻塞 ~30s 占用 1 个 blocking 线程
  ├─ 2-3 个并发 repo 操作 → 2-3 个线程耗尽
  ├─ 10 个 blocking 线程耗尽 → 新请求排队
  └─ daemon 控制连接 10s 超时 → Wrapper 报错 → 归因链中断
```

### 量化影响（基于 300KB/s 实测环境）

| 场景 | 耗时 | blocking 线程占用 | 结果 |
|------|------|-------------------|------|
| 单次 checkpoint（5MB 工作日志） | ~34s 读写 | 1 个线程 | 可接受 |
| 2 个并发 checkpoint | 各 ~34s | 2 个线程 | 开始积压 |
| checkpoint + metrics flush + git hooks | — | 5+ 个线程 | 线程池紧张 |
| daemon 启动（慢盘初始化） | 5-10s | 启动期间阻塞 | 5s 超时可能误判 |
| pre-snapshot 过期后 commit | bash in-flight 补偿 | 有限 | 依赖 bash 上下文存活 |

## 五、完整解决方案

### 5.0 立刻止血（立即执行，零代码改动）

```powershell

git-ai daemon shutdown --hard

# 2. 设置慢机环境变量
setx GIT_AI_SLOW_VM 1
setx GIT_AI_GIT_PROXY_TIMEOUT_MS 120000
setx GIT_AI_GIT_PROXY_RETRY_COUNT 0
setx GIT_AI_POST_COMMIT_TIMEOUT_MS 30000

# 3. 将 daemon 数据迁移到较快磁盘（如有）
# setx GIT_AI_DAEMON_HOME R:\git-ai-home

# 4. 为仓库添加 .git-ai-ignore 减少扫描范围
# 在仓库根目录创建 .git-ai-ignore：
target/
node_modules/
dist/
build/
.next/
coverage/
*.log
```

**说明**：

- `async_mode=false` 是最关键的止血手段——关闭 daemon，消除 blocking 线程池耗尽风险
- `GIT_AI_GIT_PROXY_RETRY_COUNT=0` 避免"超时后再重试一次"把卡顿时间翻倍
- `GIT_AI_POST_COMMIT_TIMEOUT_MS=30000` 确保 commit 后等待 30s 让 note 生成

### 5.1 代码修复（P0，不修问题反复出现）

#### 修复 1：checkpoint 真实失败必须返回非 0（P0-关键）

**文件**: `src/commands/git_ai_handlers.rs` L441, 458, 1251, 1341

当前多个失败路径 `exit(0)`，应改为：

```rust
// 不再 exit(0)，改为报告错误并返回失败码
match result {
    Ok(_) => {}
    Err(e) => {
        eprintln!("[git-ai] checkpoint failed: {}", e);
        std::process::exit(1);  // 非 0 表示失败，上层可感知并重试
    }
}
```

**原理**：错误传播链修复是所有其他机制生效的前提。如果失败返回 0，上层永远不知道需要重试。

pub fn write_all_checkpoints(&self, checkpoints: &[Checkpoint]) -> Result<(), GitAiError> {
    let tmp_path = self.checkpoints_file.with_extension("jsonl.tmp");
    let content = checkpoints.iter()
        .map(|c| serde_json::to_string(c))
        .collect::<Result<Vec<_>, _>>()?

    Ok(())
}

### 5.2 慢机专项优化（P1，明显降低挂起概率）

#### 优化 1：JSONL 改为追加写入（P1-核心）

**文件**: `src/git/repo_storage.rs`

这是最关键的性能优化，彻底消除写放大：

```rust
// 追加写入（O(1) 而非 O(n)）
pub fn append_checkpoint(&self, checkpoint: &Checkpoint) -> Result<(), GitAiError> {
    let line = serde_json::to_string(checkpoint)? + "\n";
    let mut file = OpenOptions::new()
        .create(true)
        .append(true)
        .open(&self.checkpoints_file)?;
    file.write_all(line.as_bytes())?;
    Ok(())
}

// 后台定期压缩（当文件超过阈值时异步执行）
fn maybe_compact_checkpoints(&self) {
    // 检测文件大小，超过阈值时读取 + 重写 + 保留最新记录
    // 压缩比例可通过配置控制
}

// 读取改为流式（不一次性加载全部）
pub fn read_checkpoints_for_base_commit(&self, base: &str) -> Result<Vec<Checkpoint>, GitAiError> {
    let file = fs::File::open(&self.checkpoints_file)?;
    let reader = BufReader::new(file);
    let mut results = Vec::new();
    for line in reader.lines() {
        let line = line?;
        if let Ok(cp) = serde_json::from_str::<Checkpoint>(&line) {
            if cp.base_commit == base {
                results.push(cp);
            }
        }
    }
    Ok(results)
}
```

**预期效果**: 单次 checkpoint 从阻塞 30s+ 降为毫秒级追加。

### 5.3 架构级优化（P2，长期方向）

#### 优化 7：`ai-code` 侧增加 barrier（P2）

`git-ai` 是最终一致性系统。`ai-code` 不能"调用完立即读统计"：

```powershell
function Wait-GitAiAuthorship {
    param([string]$RepoPath = ".", [int]$TimeoutSeconds = 60)
    $deadline = (Get-Date).AddSeconds($TimeoutSeconds)
    while ((Get-Date) -lt $deadline) {
        git -C $RepoPath notes --ref=ai show HEAD 2>$null
        if ($LASTEXITCODE -eq 0) { return $true }
        Start-Sleep -Milliseconds 500
    }
    return $false
}

# 使用方式：
git commit -m "Claude AI edit"
Wait-GitAiAuthorship -RepoPath "." -TimeoutSeconds 60
# 成功后再刷新 AI 占比统计
# 超时则显示"统计仍在处理中"，不要直接算成 0
```

#### 优化 8：daemon stuck watchdog（P2）

增加对以下情况的自动检测和恢复：
- control socket 可连但 `applied_seq` 长时间不推进
- checkpoint side effect 长时间无进展
- trace ingest high watermark 长时间不下降
- lock 长时间占用

触发后自动：记录错误 → 优雅 shutdown → `taskkill /F /T` → 重启 daemon。

#### 优化 9：通用 AI 上下文恢复（P2）

当前 commit replay 仅对 bash in-flight 有补偿。扩展为：
- 缓存最近一次 AI tool-use 上下文（文件路径、时间戳、agent 类型）
- 当 commit 到来但 checkpoint 缺失时，按最近有效 AI 上下文做补偿重建

#### 优化 10：Windows 单独特化运行模式（P2）

```rust
// 在 Windows 虚拟机环境下，自动降级到保守策略
if cfg!(windows) && is_slow_vm() {
    feature_flags.async_mode = false;
    feature_flags.checkpoint_wait_default = true;  // 强制同步完成
}
```

## 七、最终结论

### 问题本质

`git-ai` 在 Windows 慢虚拟机环境中的问题不是"不会统计"，而是**采集链路在多个节点上断裂**：

1. **静默失败** — `exit(0)` 让上层不知道失败，没有重试
2. **写放大崩塌** — 全量 JSONL 重写 + 多重 blob + SQLite WAL 在 300KB/s 下阻塞数秒
3. **超时预算不足** — 全链路多个超时点均未针对慢机校准
4. **无通用补偿** — checkpoint 丢失后只对 bash in-flight 有补救，普通 AI 编辑无保底

### 一句话总结

**git-ai 在 Windows 慢虚拟机场景下，是一个以"前台速度优先"设计的系统，因超时预算偏紧、写放大严重、错误静默吞噬，导致统计采集链路过早断裂，最终表现为 AI 编码占比漏统计。**

### 推荐执行路径

**如果只允许做两件事**：
1. **关闭 async 模式**（`async_mode=false`）+ **设置环境变量**（SLOW_VM、超时放大）
2. **修复 `exit(0)` 吞错** + **启用 `git_status_fallback()`**

这两项直接决定：上层能否知道失败，以及失败后还有没有补救机会。

**完整修复后**，`git-ai` 应能在 300KB/s 磁盘上以"正确性优先"模式稳定运行，统计漏记率从当前的"经常"降至"接近零"。
